# Analytics Scope Decision for Iteration 3

## Stakeholder prompt

> "Add analytics to the URL shortener."

## Why this is ambiguous

The phrase "analytics" is broad and could mean several different things:

- raw click count
- unique visitors by day
- referrer tracking
- geographic or device breakdowns
- browser / OS detection
- time-series trend reporting
- per-link traffic dashboards
- external analytics integrations

Without more detail, the requirement is underspecified and could easily expand into a much larger product feature than the project intends for this iteration.

## Interpretation for this project

For this iteration, "analytics" means:

- count how many times a short code has been resolved successfully
- record the last time the short code was used
- surface those values through a simple stats endpoint
- keep the scope in-process and in the same application domain as the existing short-link feature

This interpretation is intentionally narrow and practical for a brownfield iteration because it adds measurable value without introducing user identity tracking, external services, or complex reporting.

## Assumptions being made explicit

- No personally identifiable information will be collected.
- No third-party analytics provider or SaaS integration will be added in this iteration.
- Analytics are in-process and tied to the short-link record itself.
- Tracking is for successful `GET /{shortCode}` resolutions only.
- We are not measuring referrers, browsers, geolocation, or user cohorts yet.
- We will keep the data model simple: `clickCount` and `lastAccessedAt`.

## What is deliberately excluded

The following are intentionally out of scope for this iteration and are deferred to later work:

- unique visitor counting
- per-user or per-session analytics
- referrer or campaign attribution
- device/browser/OS breakdowns
- geographic and IP-based analysis
- time-series charts or dashboard UI
- ETL or reporting pipelines
- external analytics integrations
- any customer-facing analytics dashboard beyond a minimal stats endpoint

These exclusions are deliberate because they would materially expand the problem from a simple operational metric into a reporting or product-analytics system. This iteration is about basic link use telemetry, not full analytics instrumentation.

## Decomposition into tasks

1. Extend the persisted link model with:
   - `clickCount`
   - `lastAccessedAt`
2. On every successful `GET /{shortCode}` redirect, increment the counter and update the timestamp.
3. Add a stats endpoint such as `GET /api/stats/{shortCode}`.
4. Reuse the existing not-found handling for missing codes.
5. Add tests for:
   - click count increments on resolve
   - last access timestamp is updated
   - missing code stats return 404
   - duplicate long URL behavior still works as before
6. Document concurrency assumptions and risks.

## Concurrency decision

The counter should use an atomic increment strategy rather than read-then-write logic. This keeps click totals from being lost under concurrent requests.

In practice, this means the service should update the row in a way that preserves all increments even when many requests resolve the same short code at the same time.

## Validation and risk notes

- Concurrent requests to the same short code can lose increments if a plain read-then-write pattern is used.
- Using an atomic counter or database-level update keeps the count more accurate, but may still not be perfectly linear under extreme contention.
- Every redirect now does extra database work, which introduces a small latency trade-off.
- This is acceptable for a v1 analytics model because the requirement is to track link usage, not to optimize for extremely high throughput.

## Documentation and AI usage notes

For this iteration, the AI work should be framed as a scoping and decision-support task, not a blank-slate feature addition.

What to capture in the project docs:

- the initial ambiguous stakeholder prompt
- the chosen interpretation of analytics
- the explicit exclusions
- the concurrency and performance trade-offs
- what was generated by AI and what was hand-adjusted by the developer

This keeps the project auditable and defensible for future iteration planning.
